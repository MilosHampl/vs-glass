## Part A — Injection routes

### A0. Ground truth from this machine (read before anything else)

Reading `workbench.html` directly on this machine (`/Applications/Visual Studio Code.app/Contents/Resources/app/out/vs/code/electron-browser/workbench/workbench.html`) shows the live CSP:

```
default-src 'none';
img-src 'self' data: blob: vscode-remote-resource: vscode-managed-remote-resource: https:;
media-src 'self';
frame-src 'self' vscode-webview:;
script-src 'self' 'unsafe-eval' blob:;
style-src 'self' 'unsafe-inline';
connect-src 'self' https: ws:;
font-src 'self' vscode-remote-resource: vscode-managed-remote-resource: https://*.vscode-unpkg.net;
require-trusted-types-for 'script';
trusted-types VscodeVibrancyContinued amdLoader cellRendererEditorText collapsedCellPreview defaultWorkerFactory diffEditorWidget diffReview domLineBreaksComputer dompurify lit-html editorGhostText editorViewLayer htmlToMarkdown notebookRenderer stickyScrollViewLayer tokenizeToString notebookChatEditController richScreenReaderContent chatDebugTokenizer;
```

`VscodeVibrancyContinued` is already present in the `trusted-types` allowlist, and `out/main.js` already contains `/* !! VSCODE-VIBRANCY-START !! */ ... /* !! VSCODE-VIBRANCY-END !! */` at lines 599–604. **Vibrancy Continued is live-patched on this exact install right now.** Two load-bearing takeaways:

1. **`style-src` has `'unsafe-inline'`.** Any inline `<style>` or `style.textContent=`/`style.setProperty()` works with zero CSP patch, always, on every route. CSS is never the hard part.
2. **`script-src` has NO `'unsafe-inline'`** (only `'self' 'unsafe-eval' blob:`). A literal inline `<script>…</script>` tag is normally CSP-blocked independent of trusted-types — routes differ sharply in how they work around this (A2–A4).

I also confirmed the "corrupt installation" checksum mechanism directly: `product.json`'s `checksums` object maps 10 relative paths to a base64 SHA-256 of the *pristine* file. I recomputed SHA-256 of the on-disk (Vibrancy-patched) `workbench.html` and it does **not** match the stored value — this machine is, right now, in the checksum-mismatch state that would show the "Your Code installation appears to be corrupt" toast (the toast itself is presumably already dismissed via "Don't Show Again", since it isn't described as currently visible). The 10 checksummed paths:

```
vs/base/parts/sandbox/electron-browser/preload.js
vs/workbench/workbench.desktop.main.js
vs/workbench/workbench.desktop.main.css
vs/workbench/api/node/extensionHostProcess.js
vs/code/electron-browser/workbench/workbench.html
vs/code/electron-browser/workbench/workbench.js
vs/sessions/sessions.desktop.main.js
vs/sessions/sessions.desktop.main.css
vs/sessions/electron-browser/sessions.html
vs/sessions/electron-browser/sessions.js
```

**`out/main.js` (the Electron main-process entry, not the renderer bundle) is NOT in this list.** That is exactly why Vibrancy Continued anchors its runtime bootstrap there — but it *still* has to touch `workbench.html` for the CSP/trusted-types patch, which **is** checksummed, so it cannot avoid the corrupt-install condition either. **Conclusion that applies to every route below: there is no way to persistently ship glass.css/JS without tripping at least one checksum.** The only real variable is how many of the 4 relevant files you touch, and whether you also need a CSP/trusted-types workaround.

### A1. Custom CSS and JS Loader — `be5invis.vscode-custom-css`

- **Current status (verified via WebFetch of the Marketplace page, 2026-09-10):** version **7.5.1**, last updated **September 7, 2026** (3 days before this research), **1,190,178 installs**. Actively maintained.
- **`vscode_custom_css.imports` format:** an array of **`file://` URLs**, not plain paths — `file:///Users/you/glass.css` on macOS/Linux, `file:///C:/Users/you/glass.css` on Windows (the `C:/` is required). Confirmed from the README via WebFetch.
- **Command:** `Enable Custom CSS and JS` (Cmd+Shift+P). Must be re-run after every VS Code update and after every settings change (README, quoted verbatim: *"Every time after Visual Studio Code is updated, please re-enable Custom CSS."* / *"Every time you change the configuration, please re-enable Custom CSS."*).
- **How it actually patches (verified by WebFetch of `src/extension.js` from GitHub):**
  - Target file: **`workbench.html`** only (not the JS/CSS bundles).
  - Markers: `<!-- !! VSCODE-CUSTOM-CSS-START !! -->` … `<!-- !! VSCODE-CUSTOM-CSS-SESSION-ID <uuid> !! -->` … `<!-- !! VSCODE-CUSTOM-CSS-END !! -->`, with a `clearExistingPatches()` step that strips all markers before reapplying.
  - **It deletes the entire CSP meta tag:** `html = html.replace(/<meta\s+http-equiv="Content-Security-Policy"[\s\S]*?\/>/, "")`. This is how it "handles" trusted-types in 1.13x — not by complying with it, but by removing the whole policy, so the injected literal `<style>`/`<script>` tags (inserted into `</head>`/`</body>` as static HTML text, which browsers DO execute when parser-inserted, unlike script tags added later via `innerHTML`) run completely unrestricted.
  - No product.json/checksum patching in the source — it relies entirely on "Don't show again" or a separate Fix-Checksums extension (its own README says so verbatim: *"If Visual Studio Code complains that it is corrupted, simply click 'Don't show again' or install Fix VSCode Checksums Next."*).
  - Since files are read and inlined at patch time (not live-watched), a CSS/JS edit requires re-running "Enable Custom CSS and JS" — but because the change lives in `workbench.html` itself (loaded via `loadURL`/renderer navigation), a plain **"Developer: Reload Window"** re-fetches it from disk and picks up the new content — no full app quit needed. (This is a genuine workflow advantage over Vibrancy, see A2.)
- **Permissions (Marketplace description, WebFetch):** Windows needs Administrator mode; **macOS/Linux need the user to own the install directory** — already true here per the environment facts.
- **Open issues (WebFetch of the GitHub issues list, 2026-09-10):** only 2 open — `#285` "On Cursor Agents Window is blank" (Aug 19 2026) and `#140` "Publish extension on OpenVSX" (Mar 2021). **No open issue about trusted-types/CSP/corruption on 1.13x** — consistent with the "just delete the CSP" strategy sidestepping the whole problem category.
- **Risk, stated plainly:** this route runs the *entire* workbench renderer with **zero CSP** from the moment it patches, for the lifetime of that window session — a materially larger attack surface than Vibrancy's surgical trusted-types-allowlist edit (A2). Any other malicious/compromised extension content that would otherwise be constrained by `script-src`/`trusted-types` is no longer constrained. This is a legitimate, actively-used, well-installed tool, but it is not the "minimal blast radius" choice.
- **Uninstall:** uninstalling the extension does not automatically revert `workbench.html` (no `uninstallHook.js`-equivalent was found in the fetched source); the user must run the extension's own disable/restore path first, or manually restore `workbench.html` from a VS Code reinstall.

### A2. Vibrancy Continued — `illixion.vscode-vibrancy-continued` (already installed, 1.1.93)

Read directly from the installed extension (`extension/index.js`, `extension/file-transforms.js`, `runtime/index.mjs`, `readme.md`, `AGENTS.md`, `package.json`, `package.nls.json`) plus live evidence on this machine.

**`vscode_vibrancy.imports`:** an array of **plain file paths** (not `file://` URLs — confirmed by `package.nls.json`: `"configuration.imports.description": "Import CSS/JS files, as file paths."`, and by `index.js` line ~740: `fs.readFile(config.imports[i], 'utf-8')` with no URL parsing). This is a real, easy-to-get-wrong difference from Custom CSS Loader's `file://` requirement — mixing the two conventions across extensions is a likely footgun for the README.

**How it patches (verified by reading the source):**
- `out/main.js` (Electron main process, NOT checksummed) gets the runtime bootstrap injected between `/* !! VSCODE-VIBRANCY-START !! */` / `/* !! VSCODE-VIBRANCY-END !! */` markers (confirmed present at lines 599–604 on this machine).
- `workbench.html`'s CSP meta tag gets `trusted-types` extended to include the literal policy name `VscodeVibrancyContinued` (function `patchCSP` in `file-transforms.js`, confirmed present in the live CSP dump in A0). If no `trusted-types` directive exists yet, it appends one; if the directive already lists the legacy (non-"Continued") policy name, it's cleaned up first.
- At `BrowserWindow` creation, the injected main-process code calls **`window.webContents.executeJavaScript(...)`** — this evaluates code directly in the renderer's V8 context from the *privileged* Electron main process side, which is understood to bypass the page's own CSP/trusted-types enforcement (a widely-documented Electron CSP-bypass characteristic of `executeJavaScript`). Inside that executed string, it does:
  ```js
  const vscodeVibrancyTTP = window.trustedTypes.createPolicy("VscodeVibrancyContinued", { createHTML: v => v });
  const styleElement = createElement("div");
  styleElement.innerHTML = vscodeVibrancyTTP.createHTML(JSON.stringify(styleHTML()));
  document.body.appendChild(styleElement);
  // ...same pattern for scriptElement / scriptHTML()
  ```
  where `styleHTML()` returns a literal `<style>` block containing the theme CSS **and** `config.imports.css` (each user-supplied `.css` import file's content, read and inlined at patch time), and `scriptHTML()` returns `app.imports.js` similarly wrapped in `<script>`.
- **Caveat worth flagging for the README:** per the HTML parsing spec, a `<script>` element inserted via `.innerHTML` assignment does **not** execute (browsers only run parser-inserted scripts). The CSS half of this mechanism is confirmed working (that's the whole point of the extension); the JS half (`config.imports` `.js` files) may not reliably execute through this exact code path — worth testing empirically before depending on Vibrancy's JS-import feature for glass.css's toggle-class script (see Part C).
- Because the CSS/JS content is inlined into `out/main.js` (the *main process* file, loaded once at Electron app launch), **a plain "Reload Window" does NOT pick up a glass.css edit** — `out/main.js` isn't re-read until the whole app is quit and relaunched. This is the opposite of Custom CSS Loader's `workbench.html`-based approach (A1), which does refresh on a window reload. Practical implication for iterative glass.css development: **prefer Custom CSS Loader for the edit-reload-look loop, and reserve Vibrancy purely for what only it can do (native OS vibrancy material).**
- **Update survival:** re-run the `Reload Vibrancy` command after every VS Code update, then restart (README, quoted: *"Each time VS Code is updated, please re-enable Vibrancy using the same steps."*).
- **Uninstall:** command `Disable Vibrancy`, or simply uninstalling the extension and restarting VS Code auto-removes the patches (`extension/uninstallHook.js` exists specifically for this — 25KB of cleanup logic that runs on extension deactivation/uninstall).
- **Corrupt-install warning:** same story as every route — README says click "Don't Show Again", or install Fix VSCode Checksums Next (A5) if that option isn't offered or the `[Unsupported]` title-bar badge needs clearing too.
- **macOS-specific gotchas found in the README (quoted):**
  - *App Translocation / read-only bundle*: `EROFS: read-only file system` — "Your installation of VSCode is affected by App Translocation. To fix this, either use the Finder and move VSCode to `/Applications`... or run `sudo xattr -dr com.apple.quarantine "/Applications/Visual Studio Code.app"`." This is the **real** macOS gotcha (not Gatekeeper/codesigning re-verification — see A6) — a freshly-downloaded, not-yet-quarantine-cleared `.app` gets mounted read-only by Gatekeeper's App Translocation until moved into `/Applications` or the quarantine xattr is stripped.
  - *Full screen / Zen Mode*: native full screen moves the window to its own Space with nothing behind it, so vibrancy goes flat; "wallpaper tinting" (System Settings → Appearance) is the only partial mitigation, and only in certain vibrancy `type`s. `"zenMode.fullScreen": false` keeps Zen Mode in a normal (still-vibrant) window.
  - A **`diagnose.sh`** read-only diagnostic script is provided (`curl -fsSL https://raw.githubusercontent.com/illixion/vscode-vibrancy-continued/main/scripts/diagnose.sh | bash`) to check which patches actually landed — useful to adopt as a debugging step in our own README.
- **Can Custom CSS Loader and Vibrancy coexist?** They patch different files for their core mechanism (Vibrancy: `out/main.js` + a CSP-*extend*; Custom CSS Loader: `workbench.html` body/head + a CSP-*delete*), so there's no marker-string collision. But **both touch the same CSP meta tag region of `workbench.html`**, and their strategies conflict: if Custom CSS Loader runs after Vibrancy and deletes the CSP entirely, Vibrancy's own `trusted-types` allowlist edit is simply gone too — harmless in practice, since a *missing* CSP is even more permissive than Vibrancy's extended one (nothing left to enforce `createPolicy`'s allowlist against). If Vibrancy's `patchCSP` runs *after* Custom CSS Loader already removed the meta tag, its regex finds no meta tag (`noMetaTag: true`) and silently does nothing — again harmless, since there's no CSP left to need patching. **Net: installing both should not break either's core function, but re-running "last one wins" is the safe operating procedure** — this has not been tested live on this machine (would require actually installing Custom CSS Loader, outside this research's scope), so treat it as a reasoned inference, not a verified fact.
- **On THIS machine specifically:** since Vibrancy is already installed and active, `vscode_vibrancy.imports` is the lowest-friction way to ship glass.css **today**, with the important caveats above about (a) `file:///`-vs-plain-path config format and (b) full-app-restart-not-window-reload for edits. Its own theme CSS sets a handful of selectors `!important`-transparent for the native vibrancy material to show through (found while reading `themes/` and `themes/fixes/` — not fully enumerated here since the user's current `vscode_vibrancy.theme` choice determines which stylesheet is active; recommend `themes/*.css` be diffed against `selector-map.json`'s region list before writing glass.css, to avoid `!important` fights).

### A4. Our own direct patch script (`scripts/inject.sh`)

Feasibility assessment, informed by A0's checksum findings and by how a newer, actively-maintained alternative (`subframe7536/vscode-custom-ui-style`, see A5) does it:

- **Cleanest injection point for CSS:** append glass.css directly to the end of the already-linked `workbench.desktop.main.css` (loaded via `<link rel="stylesheet" href="../../../workbench/workbench.desktop.main.css">` in `workbench.html`, confirmed by reading the file). Since `style-src` already has `'self'` and `'unsafe-inline'`, this needs **zero** CSP/trusted-types workaround — it's the same mechanism the browser already trusts for the file it's already loading. This is objectively simpler than Custom CSS Loader's and Vibrancy's CSS routes, which both round-trip through `workbench.html` and either delete or extend the CSP.
- **Cleanest injection point for JS (toggle class + SVG filter defs):** append a small IIFE to the end of `workbench.js` (the tiny, 409-line ES-module bootstrap referenced by `<script src="./workbench.js" type="module">` in `workbench.html`) or to `workbench.desktop.main.js`. Because it's a same-origin **file**, not a runtime-injected inline `<script>` tag or an `innerHTML` sink, it is governed only by `script-src 'self'` (already satisfied) and is **not** a trusted-types-guarded sink at all (trusted-types only guards runtime APIs like `.innerHTML =`, `.src =`, `eval(string)` — not the browser's normal parsing of a `<script src>` resource). This sidesteps the entire CSP/trusted-types problem that both A1 and A2 have to work around.
- **Idempotency/reversibility:** use the same marker-comment convention as the existing tools (e.g. `/* VS-GLASS-START */ ... /* VS-GLASS-END */` for CSS, and an equivalent for JS), with a regex-based `MARKER_REGEX` strip-then-reinsert on every run (exactly Vibrancy's and Custom CSS Loader's pattern) — makes re-running `inject.sh` safe, and an `inject.sh --uninstall` trivial (strip markers, done).
- **Checksum fix, required either way:** since `workbench.desktop.main.css` and (if used) `workbench.js`/`workbench.desktop.main.js` are all in `product.json`'s `checksums` map (A0), `inject.sh` should also recompute and rewrite those two/three entries in `product.json` after patching — i.e., build in the "Fix VSCode Checksums" behavior rather than depending on a separate extension. The hash format, confirmed by reproducing it locally: standard base64 (with `+`/`/`, not URL-safe) of the raw SHA-256 digest, **with `=` padding stripped**. Verified the encoding shape by computing `sha256(workbench.html)` and comparing byte format against the stored value (values didn't match content-for-content only because the on-disk file is *already* Vibrancy-patched, not because the encoding differs — the produced string has the same base64 alphabet/length pattern as the stored entries).
- **Backup:** copy the 2–3 touched files to `<file>.vs-glass-backup` before first patch (mirroring Custom UI Style's `.custom-ui-style`-suffix backup convention, A5) so `--uninstall` can do a byte-exact restore instead of relying on marker-stripping alone (belt-and-suspenders for a file that's also checksum-tracked).
- **Update survival:** VS Code's own updater replaces the whole `Contents/Resources/app` tree (or at least these specific files) on update, silently discarding our patch and our `product.json` checksum edits. `inject.sh` needs to be re-run after every VS Code update — no different from every other route (A1–A3 all say the same in their own READMEs). Consider a `postinstall`/launch-time check (compare a version marker embedded in our own comment block against the running VS Code version) that prompts the user to re-run.
- **Does NOT trigger a *worse* corrupt-install experience than the others** — it triggers exactly the same class of warning (fixed by our own `product.json` checksum rewrite, built in) and, unlike A1, doesn't need to touch or delete the CSP at all if we stick to the CSS-only + same-origin-JS-file routes above.
- **Recommended shape for `scripts/inject.sh`:** `inject.sh install|uninstall|status`. `install`: locate app bundle (respect `$VSCODE_APP_PATH` override, default the two conventional macOS paths), back up files, strip old markers, append new marker block(s), recompute + rewrite the relevant `checksums` entries in `product.json`, print a restart reminder. `status`: diff current file hashes against our last-known-good backup to report drift (e.g., after a VS Code update). `uninstall`: restore from backup verbatim.

### A5. Any new official mechanism? (checked, as instructed)

**No general-purpose official custom-CSS API exists in VS Code 1.136.1.** What I found instead, by grepping the live `workbench.desktop.main.js` for `workbench.experimental.*` settings (verified by grep, not memory):

- `workbench.experimental.modernUI` — **currently live**, `type:"boolean", default:false`, with schema flag `experiment:{mode:"auto"}` (Microsoft's own experimentation service can A/B-flip this without user opt-in). Official description, extracted from `nls.messages.json` index 7076: *"Controls whether the Modern UI Update is enabled. When on, the side bars and bottom panel are shown as floating cards with rounded corners and gaps, and a set of refreshed workbench styles is applied, matching the Agents window design."* This is a **binary full-theme re-skin**, not a CSS injection point.
- `workbench.experimental.floatingPanels` — appears **only** in a `ConfigurationMigration` entry (`registerConfigurationMigrations`) that forwards any old truthy value into enabling `modernUI`. **No live schema** for it anymore in 1.136.1 — it's been folded into `modernUI`.
- `workbench.experimental.styleOverrides` — also appears **only** in that same migration list, described there as an array-typed value (`Array.isArray(s)&&s.length>0`) that, if previously set, also gets forwarded into enabling `modernUI` and then discarded. **This is the closest VS Code has come to an official granular style-override hook** — it existed as a setting at some point before this build and has since been **removed/collapsed**, not expanded. Grepping for a current schema entry (`"workbench.experimental.styleOverrides":{`) returns nothing in this build.
- A companion flag `workbench.experimental.modernUIUppercaseViewHeaders` and unrelated `requestHidDevice`/`requestSerialPort`/`requestUsbDevice` experimental flags also exist, confirming `workbench.experimental.*` is Microsoft's general "unstable settings" namespace, not evidence of a customization API in progress.
- **Web search** ("vscode custom css API 2026 workbench.experimental proposal official support") turned up nothing beyond the same community extensions already covered — no Microsoft roadmap item, proposal, or issue for a supported custom-CSS API was found.

**Conclusion: confirmed, as expected — no supported mechanism exists.** The practical implication for glass.css is that it must keep targeting **both** the classic layout selectors **and** the `.modern-ui`/`.floating-panels` variants (see `selector-map.json`), because `modernUI` can be silently auto-enabled by Microsoft's experimentation service on a subset of users, including possibly this one, at any point without any explicit opt-in.

### A6. macOS-specific gotchas (codesigning/Gatekeeper, `/Applications` permissions, Settings Sync)

- **Ownership/`/Applications` permissions:** on this machine the app is **owned by the user, no sudo needed** (per environment facts) — this is the normal case for a single-user, drag-installed VS Code on macOS (unlike a Windows Program-Files-style install, or a Linux distro package under `/usr/share`), so none of A1–A4's patch-writing needs elevated privileges here. This is *not* universal — a machine where VS Code was installed by a different admin account, or via an MDM-managed install, could have `/Applications/Visual Studio Code.app` owned by `root`/another user, in which case `sudo chown -R $(whoami) "/Applications/Visual Studio Code.app"` (the exact command found in Custom UI Style's README troubleshooting, A5-adjacent) is the documented fix across every tool surveyed.
- **App Translocation, not Gatekeeper re-verification, is the real day-to-day gotcha:** macOS Gatekeeper's "App Translocation" mounts a freshly-downloaded (still-quarantined) `.app` at a randomized **read-only** path until it's moved into `/Applications` (or the quarantine xattr is stripped). This produces `EROFS: read-only file system` errors from any of these patchers, independent of ownership — Vibrancy's README documents this exact failure mode and its fix (`sudo xattr -dr com.apple.quarantine "/Applications/Visual Studio Code.app"`, or simply move-out-then-back-into `/Applications` via Finder).
- **Does modifying files inside the `.app` bundle re-trigger Gatekeeper on every subsequent launch?** From general Gatekeeper/codesign documentation (WebSearch, no VS-Code-specific source found): Apple's code signature is a hash-manifest **seal** over the bundle's contents, and modifying files after signing does invalidate that seal for tools like `codesign --verify`/`spctl --assess`. However, Gatekeeper's *enforcement* of that seal is primarily a **first-launch / quarantine-attribute** check (tied to `com.apple.quarantine`, cleared once by translocation-then-approval, or by `xattr -d`), not a continuous per-launch integrity re-scan of every internal file on every subsequent run — Electron apps do not routinely self-verify their own resource signatures at startup, and none of the four tools surveyed (Custom CSS Loader, Vibrancy, APC, Custom UI Style) describe needing to re-sign or `codesign --force --deep --sign -` the app after patching. **VS Code's own `product.json` `checksums` mechanism (A0) is its self-built substitute for exactly this kind of internal integrity check, decoupled from Apple's system-level Gatekeeper** — which is why the "corrupt installation" warning is a VS Code-level notification, not a macOS Gatekeeper block. This section is marked partly "Assumed" below since no source confirms VS Code/Electron's exact runtime Gatekeeper-interaction behavior with certainty; it is inferred from (a) the consistent absence of any re-signing step across four independent real-world tools, and (b) general Gatekeeper documentation about when its checks fire.
- **Settings Sync interactions:** VS Code's Settings Sync syncs `settings.json` values (including extension-contributed settings like `vscode_custom_css.imports` / `vscode_vibrancy.imports`), the installed-extensions list, keybindings, snippets, and some UI state — but it does **not** sync the actual file patches made to the app bundle (those are local filesystem mutations on the machine where the enable-command was run). Practical consequence: syncing settings to a second machine will carry over the `imports` **file paths**, which are very likely wrong on that machine (different username/home directory) — and even if correct, the extension's "Enable ..." command still has to be run locally on the new machine to actually patch its files, since Settings Sync has no mechanism to execute that step remotely. This matches general Settings Sync documentation (code.visualstudio.com/docs/getstarted/settings) plus the two extensions' own `file://`/path-based config design; the specific claim about whether the "Don't Show Again" notification-dismissal flag itself participates in UI-state sync was not directly confirmed from a source and should be treated as unverified.

### A7. README recommendation

- **Primary route: Vibrancy Continued's `vscode_vibrancy.imports`, for this machine, today** — it's already installed and active, and it's the only route of the four that also gives native OS-level vibrancy (the actual "blur what's behind the window" effect that CSS alone cannot produce — see `selector-map.json`'s `stackingContext`). Ship glass.css through its `imports` array (plain file paths, not `file://`), and treat "Reload Vibrancy" + full app restart as the deploy step.
- **Fallback / faster-iteration route: Custom CSS and JS Loader (`be5invis.vscode-custom-css`)** — actively maintained (v7.5.1, Sept 7 2026), huge install base, and its `workbench.html`-based patch refreshes on a plain window reload, making it much better for the CSS edit-reload-look loop while developing glass.css. Its `imports` need `file://` URLs. Accept its stated risk (full CSP removal) as a documented tradeoff for a smoother dev loop, and switch the *shipped*, end-user-facing instructions back to Vibrancy once glass.css stabilizes.
- **Do not recommend APC Customize UI++** — de facto unmaintained since August 2024, with an open, unaddressed incompatibility report over a year old as of this writing.
- **Longer-term: our own `scripts/inject.sh`** is worth building specifically because it can inject CSS with *zero* CSP/trusted-types workaround (append to `workbench.desktop.main.css`, already `'self' 'unsafe-inline'`-permitted) and JS with zero workaround too (append to `workbench.js`, already `script-src 'self'`-permitted, and not a trusted-types sink at all) — a smaller, more auditable blast radius than either A1 or A2, at the cost of us owning the checksum-rewrite and update-survival logic ourselves.
- **Plainly-stated risk section for the README:**
  1. **Every route touches a checksummed core file** and will show the "Your Code installation appears to be corrupt" / `[Unsupported]` notice until dismissed ("Don't Show Again") or fixed (Fix VSCode Checksums Next, or our own `inject.sh`'s built-in checksum rewrite). This is expected and cosmetic, not a sign of real corruption — but it is a genuine trust signal we are asking the user to override.
  2. **Custom CSS Loader's mechanism deletes the workbench's entire CSP** for the process lifetime — a real, if narrow (main renderer only, not webviews/extension host), reduction in defense-in-depth. Document this explicitly if we recommend it even as a fallback.
  3. **Every route breaks on every VS Code update** and must be manually re-applied — this is not a one-time setup step, it's ongoing maintenance the user signs up for.
  4. **`workbench.experimental.modernUI` can be silently A/B-enabled by Microsoft** (`experiment:{mode:"auto"}`), changing dozens of selectors' classes/margins/radii out from under glass.css without any user action. glass.css must be written against both layouts (`selector-map.json` documents both).
  5. **Settings Sync will not follow you across machines correctly** — `imports` paths are local and will need to be redone per-machine.

## Part B — see `research/selector-map.json`

The selector map was produced by scanning the real, installed `workbench.desktop.main.css` (1,568,985 bytes, minified to ~37 physical lines) for each requested selector substring and capturing the enclosing CSS rule(s) verbatim, plus targeted greps of `workbench.desktop.main.js` for the runtime CSS-variable-injection mechanism. Headline findings (full detail and per-region data in the JSON):

1. **Every VS Code theme color is exposed as `--vscode-<key-with-dots-as-dashes>` on `.monaco-workbench`**, confirmed two ways: the naming function `function CH(s){return \`--vscode-${s.replace(/\./g,"-")}\`}`, and its caller `ThemeService.updateDynamicCSSRules`, which builds one big rule `.monaco-workbench { --vscode-editor-background: ...; --vscode-sideBar-background: ...; }` and writes it into a runtime-created `<style class="contributedColorTheme">` element in `document.head` (via `.textContent =`, not `innerHTML`) — **not** in the static CSS bundle at all. This regenerates on every theme change. See `selector-map.json.cssVariableSystem`.
2. **`.monaco-workbench` itself is `overflow:hidden` and fills the window** (`position:relative;inset:0;z-index:1`), and **sidebar/editor/panel/auxiliarybar are non-overlapping `.split-view-view` siblings** positioned by inline styles from the JS layout engine (`position:absolute`, no z-index). **A `backdrop-filter` on `.part.sidebar` cannot blur the editor** — nothing is painted behind the sidebar in the same document layer except `.monaco-workbench`'s own flat background (or an image, if glass.css sets one). This directly answers the task's central question; full reasoning and the three concrete strategies (shared backdrop-image, native OS vibrancy, or targeting the floating/overlay widget layer where true overlap exists) are in `selector-map.json.stackingContext`.
3. **The floating/overlay widget layer (quick-input, context-view/menus, notifications, hover, suggest, parameter-hints, rename-box, peekview, find-widget, sticky-widget, debug-toolbar) genuinely overlaps editor/part content** (`position:absolute`/`fixed`, z-index 4–2575, full table in `selector-map.json.domOverlayLayers`) — this is where `backdrop-filter` produces a real, non-fake blur, and should be the primary target for glass.css's `backdrop-filter` budget.
4. **No structural container uses CSS `contain`** (only 3 unrelated hits in the whole 1.5MB bundle: a notebook toolbar, an icon grid, and a chat "thinking box"), and the only `transform`s found are cosmetic/localized (a progress bar, notebook output, an icon spinner, and one `floating-panels` activity-bar nudge) — **containment/transform are not a general blocker** for backdrop-filter stacking anywhere in the main layout.
5. **VS Code 1.136.1 ships an experimental "Modern UI" re-skin** (`workbench.experimental.modernUI`, default off but `experiment:{mode:"auto"}` — Microsoft can silently A/B it on) that adds `.modern-ui`/`.floating-panels`/`.modern-ui-compact` classes to `.monaco-workbench`, turning sidebar/panel/activitybar into margined, bordered, rounded "floating cards" with their own `background-color: var(--vscode-surface-background) !important`. glass.css needs to handle both the classic and modern-ui layouts — `selector-map.json.importantContext2026` and the per-region `notes` fields flag every place this matters.

## Part C — DOM mount points and toggle-class feasibility

(Full data: `selector-map.json.domOverlayLayers.mountPoints` and the `regions.quickInputWidget` / `regions.contextView` / `regions.notificationsToasts` / `regions.notificationsCenter` entries.)

- **`.context-view`** hosts anchored dropdowns/menus/`.monaco-menu` — two variants, `.context-view{position:absolute}` (anchored) and `.context-view.fixed{position:fixed}` (viewport-anchored); confirmed a `.monaco-workbench` descendant via `.monaco-workbench .context-view{-webkit-app-region:no-drag}`.
- **`.quick-input-widget`** — `position:absolute;left:50%;z-index:2550`, sized against `.monaco-workbench`'s own `position:relative` ancestor.
- **`.notifications-toasts` / `.notifications-center`** — confirmed **direct children** of `.monaco-workbench` via the `>` combinator (`.monaco-workbench>.notifications-toasts{...}`), z-index 2545.
- **z-index ranges** run from 4 (sticky-widget, a subtle in-editor overlay) up to 2575 (`.monaco-dialog-modal-block`) and spike to 100000 for screencast-mode overlays — full table in the JSON.
- **`.monaco-workbench` is the class-toggle root, not `<body>`.** Confirmed by grep: every platform/theme/feature-flag class VS Code itself applies (`.mac`, `.vs`/`.vs-dark`/`.hc-black`/`.hc-light`, `.modern-ui`, `.floating-panels`, `.modern-ui-compact`, `.nosidebar`, `.nopanel`, `.monaco-enable-motion`, etc.) lands on `.monaco-workbench`, not `<body>` (body stays an empty `<body aria-label="">` wrapper per `workbench.html`; `.monaco-workbench` is created and appended into it at runtime by the workbench bootstrap). **A `.monaco-workbench.vs-glass` toggle class, added by a small injected script, is the idiomatic, precedented approach** — it composes naturally with every selector already in `selector-map.json` (e.g. `.monaco-workbench.vs-glass .part.sidebar { ... }`).
- **Is a tiny JS file (add class + inject SVG filter defs) feasible under the trusted-types CSP?** Yes, via two different mechanisms, both already proven in the wild on this exact CSP:
  - **Vibrancy Continued's own runtime** does it via `BrowserWindow.webContents.executeJavaScript(...)` from the privileged Electron main process (bypasses page CSP/trusted-types entirely) plus an explicit `trustedTypes.createPolicy(...)` + `.innerHTML =` for anything it does insert into the DOM at runtime. This requires a native-messaging-capable extension (main-process code), not pure page-script.
  - **A same-origin static file edit** (our own `inject.sh` route, A4) — appending an IIFE directly into `workbench.js` or `workbench.desktop.main.js` — needs **no** trusted-types policy and **no** CSP change at all, because trusted-types only guards runtime sinks (`.innerHTML=`, `.src=`, `eval(string)`) and CSP `script-src 'self'` already permits the browser's normal parsing/execution of that same-origin file. This is the simplest, lowest-risk path for the toggle-class script specifically: `document.querySelector('.monaco-workbench')?.classList.add('vs-glass')`, plus building and appending an `<svg>` filter-defs block via `document.createElementNS`/`appendChild` DOM calls (not `innerHTML`, so it never needs a trusted-types policy at all — element/attribute creation via the DOM API is never a guarded sink, only string-to-HTML/Script coercion is).
  - Custom CSS Loader's `imports` JS files execute the same way its CSS does — inlined as a literal, parser-inserted `<script>` tag into `workbench.html`, which works precisely because it has already deleted the CSP (A1) — so no trusted-types policy is needed there either, but only because there is no CSP left to enforce one.
